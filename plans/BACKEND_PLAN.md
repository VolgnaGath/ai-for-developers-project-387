# План реализации backend

Документ фиксирует согласованный дизайн до начала реализации. Backend пока отсутствует; сначала уточняется контракт, затем из него генерируется код и только после этого пишется бизнес-логика.

## Скоуп и ограничения

- Backend предназначен для локальной демонстрации или закрытого стенда.
- Авторизации в v1 нет, включая административные операции.
- Хранилище эфемерное: все брони и пользовательские изменения типов событий теряются при перезапуске.
- Поддерживается только один Node.js-процесс. Несколько реплик с in-memory storage запускать нельзя.
- Новые продуктовые возможности и изменения API вне перечисленных в этом документе перед реализацией отдельно согласуются.

## Стек

- Node.js 24 LTS с зафиксированным `engines.node`.
- TypeScript и ESM.
- Express 5.
- `@nahkies/openapi-code-generator`, шаблон `typescript-express`, для генерации router, типов и runtime-валидации.
- Zod 4 для сгенерированной runtime-валидации запросов и ответов.
- `@js-temporal/polyfill` для календарной логики.
- Vitest + Supertest.
- In-memory `Map` для типов событий и броней.

Цепочка остаётся contract-first:

```text
main.tsp
  -> npm run generate
  -> tsp-output/schema/openapi.yaml
  -> генерация frontend-типов и backend router/types/validators
  -> ручная реализация бизнес-логики
```

Backend-код генерируется именно из закоммиченного `tsp-output/schema/openapi.yaml`, общего для frontend и backend. Express только монтирует сгенерированный router: маршруты, параметры, тела, статусы и ответы вручную не дублируются. Сгенерированный router валидирует запросы и ответы; ошибка в ответе handler считается внутренней ошибкой.

Официальный `@typespec/http-server-js` пока alpha/preview, поэтому он не используется как основа проекта.

## Контракт

Перед реализацией изменить `main.tsp` и перегенерировать OpenAPI и frontend-типы:

- Добавить `BadRequest` с `400` и `code: "bad_request"` всем операциям с body или query validation.
- `400` использовать для malformed JSON, отсутствующих или неверных полей, неверных query-параметров и диапазона `from > to`.
- Оставить `422 invalid_slot` только для синтаксически корректного `start`, который не является базовым кандидатом.
- Оставить `409 slot_unavailable` для корректного базового кандидата, который уже занят.
- Добавить `409 event_type_duration_locked` для попытки изменить длительность типа события, у которого есть бронь.
- `409 event_type_has_bookings` оставить только для удаления типа события.
- Добавить `PayloadTooLarge` с `413` и `code: "payload_too_large"` для стандартного лимита `express.json()` в `100kb`; отдельный пользовательский лимит не настраивать.
- Добавить `InternalError` с `500` и `code: "internal_error"` в результат каждой операции, включая health check.
- Добавить `GET /health` с ответом `200 { "status": "ok" }`.
- Сохранить `200` для создания типа события и брони и `204` для удаления типа события.
- Зафиксировать включительность `from` и `to`.
- Описать окно бронирования как сегодня и следующие 13 календарных дат в `PublicConfig.timezone`.
- Убрать утверждение, что возвращаемые кандидаты никогда не пересекаются.
- Явно указать общую занятость владельца между всеми типами событий.
- Зафиксировать, что timestamps в ответах сериализуются в UTC с `Z`; входной timestamp может содержать любой корректный offset.
- Добавить строковые ограничения из раздела «Нормализация данных».
- Разрешить `guestEmail: ""` только в `BookingInput`; backend преобразует его в отсутствие значения, а `Booking` никогда не возвращает пустой email.

Неизвестный API-маршрут или метод возвращает `404 { "code": "not_found" }`, а не HTML Express. Неожиданные ошибки не раскрывают технические детали и возвращают `500 { "code": "internal_error" }`.

## Календарные правила

- Весь календарь живёт в `PublicConfig.timezone`, как зафиксировано в ADR `docs/adr/0001-calendar-in-config-timezone.md`.
- `from` и `to` — включительные календарные даты в таймзоне конфига.
- Диапазон дат реализуется как полуинтервал `[from@00:00, dayAfter(to)@00:00)` в таймзоне конфига.
- Окно бронирования включает сегодня и следующие 13 календарных дат.
- Корректный диапазон `listSlots`, целиком лежащий вне окна, возвращает `200 []`.
- Прошедшие старты текущего дня исключаются; старт ровно в `now` допустим.
- Сетка начинается от `workingHours.start`, кандидаты начинаются каждые `slotStepMinutes`.
- Слот должен полностью помещаться в рабочие часы.
- При длительности 30 минут и шаге 15 минут кандидаты могут пересекаться.
- Любая бронь блокирует пересекающиеся слоты всех типов событий: занятость владельца общая.
- Пересечение определяется по полуинтервалам `[start, end)`; смежные слоты не пересекаются.
- Входной timestamp сравнивается как момент времени, поэтому эквивалентные offsets принимаются.
- `start` должен точно совпасть с вычисленным кандидатом; произвольные секунды и миллисекунды делают слот невалидным.
- Несуществующие локальные старты при переходе DST пропускаются.
- При повторе локального времени оба реальных момента сохраняются, если входят в рабочее окно.
- Backend возвращает слоты и брони хронологически.
- API timestamps возвращаются в UTC с `Z`; frontend отображает их в таймзоне конфига.

`listBookings(from, to)` фильтрует по календарной дате `Booking.start` в таймзоне конфига:

- только `from` — все брони с этой даты включительно;
- только `to` — все брони до этой даты включительно;
- обе границы — включительный диапазон;
- без границ — все брони.

## Типы событий и брони

- После каждого запуска создаются два демонстрационных типа события без броней: «Консультация» на 30 минут и «Онбординг» на 15 минут.
- Seed использует стабильные ID с префиксом `evt_`.
- Новые ID непрозрачны для клиента и строятся из UUID с префиксами `evt_` и `bk_`; публичная гарантия конкретного формата не даётся.
- Дублирующиеся заголовки типов событий разрешены.
- Типы событий возвращаются в порядке создания, seed — первыми; порядок не закрепляется как гарантия API.
- Редактирование не меняет позицию типа события в порядке создания.
- Название и описание типа события с бронями можно менять.
- Изменение `durationMinutes` запрещено, если существует хотя бы одна бронь этого типа.
- Удаление типа события запрещено, если существует хотя бы одна бронь этого типа.
- Прошедшие брони также блокируют изменение длительности и удаление: исторические данные не теряют согласованность.

## Нормализация данных

Backend обрезает внешние пробелы у всех пользовательских строк до сохранения:

- `EventTypeInput.title`: обязательное непустое после trim, максимум 100 символов;
- `EventTypeInput.description`: максимум 1000 символов;
- `BookingInput.guestName`: обязательное непустое после trim, максимум 100 символов;
- `BookingInput.guestEmail`: корректный email максимум 254 символа либо пустая строка.

Пустые после trim `description` и `guestEmail` преобразуются в отсутствие поля. Email сохраняется в исходном регистре, без приведения к lowercase.

## Runtime-конфиг

Календарная доступность фиксирована в коде:

```text
timezone: Europe/Moscow
working days: Monday-Friday
working hours: 09:00-18:00
booking window: 14 calendar dates
slot step: 15 minutes
```

Переменные окружения:

- `PORT`, по умолчанию `4010`;
- `HOST`, по умолчанию `127.0.0.1`; внешний bind включается только явно;
- `FRONTEND_ORIGIN`, по умолчанию `http://localhost:5173`.

CORS разрешает один точный origin, без credentials и wildcard. Для другого `Origin` CORS-заголовки не добавляются; backend не обязан самостоятельно отклонять такой запрос. Запросы без `Origin`, включая CLI-клиенты, работают.

## Структура

```text
backend/
├── src/
│   ├── generated/        # router, API-типы, Zod-схемы
│   ├── app.ts            # Express, CORS, error mapping
│   ├── server.ts         # env, запуск и graceful shutdown
│   ├── config.ts         # фиксированная доступность
│   ├── store.ts          # in-memory Map и seed
│   ├── calendar.ts       # генерация и проверка слотов
│   └── handlers.ts       # реализация operationId
├── test/
├── package.json
├── tsconfig.json
└── Dockerfile
```

Дополнительные слои и repository-интерфейсы пока не нужны. `store.ts` можно заменить адаптером БД позднее.

`backend/src/generated/` коммитится, вручную не редактируется. CI повторяет генерацию и проверяет отсутствие diff вместе с OpenAPI и frontend generated types.

## Ключевые алгоритмы

Для получения слотов:

1. Найти тип события или вернуть `404`.
2. Проверить формат и порядок диапазона дат.
3. Пересечь диапазон с окном бронирования.
4. Для рабочих дней построить старты от `workingHours.start` с шагом `slotStepMinutes`.
5. Оставить слоты, полностью помещающиеся в рабочие часы.
6. Исключить прошедшие старты.
7. Исключить кандидаты, пересекающиеся с любой бронью.
8. Вернуть результат хронологически и сериализовать timestamps в UTC.

Для создания брони:

1. Найти тип события или вернуть `404`.
2. Проверить входной старт как базовый кандидат без учёта занятости.
3. Если старт не соответствует сетке, окну или рабочим часам, вернуть `422`.
4. Атомарно проверить пересечения со всеми бронями.
5. При пересечении вернуть `409`.
6. Без `await` между проверкой и добавлением создать бронь.
7. Рассчитать `end`, `createdAt`, `status` и ID на сервере.

Такая операция атомарна только для одного Node.js-процесса.

## Ошибки и процесс

- Ошибки request validation сгенерированного router и JSON parser преобразуются в контрактные `400` или `413`.
- Ошибки handler и response validation преобразуются в `500 internal_error`.
- Логируются запуск сервера и неожиданные `500`; отдельная logging-библиотека и access logs в v1 не нужны.
- `SIGINT` и `SIGTERM` прекращают приём новых запросов и корректно закрывают HTTP-сервер.
- Health check проверяет только готовность процесса: внешних зависимостей и БД нет.

## Тестирование

Clock и генерация ID внедряются как зависимости там, где это необходимо для детерминированных тестов. Store создаётся заново для каждого теста.

Unit-тесты покрывают:

- границы рабочего дня и окна бронирования;
- выходные;
- начало сетки относительно `workingHours.start`;
- старт ровно в `now` и прошедшие старты;
- смену DST, включая пропущенные и повторяющиеся локальные времена;
- пересечения 15- и 30-минутных слотов;
- общую занятость между разными типами событий;
- эквивалентные offsets, секунды и миллисекунды;
- включительные диапазоны броней и слотов;
- нормализацию строк.

HTTP integration-тесты покрывают все операции и статусы `200`, `204`, `400`, `404`, `409`, `413`, `422`, `500`, включая malformed JSON, response validation, двойное бронирование, изменение длительности и удаление типа с прошедшими или будущими бронями.

Frontend generated types, классификатор ошибок, unit-тесты и MSW приводятся в соответствие с окончательным контрактом. MSW должен повторять включительность `to`, общую занятость и пересечения, а не хранить только точные старты.

Добавляется отдельный Playwright smoke-набор с реальным backend без MSW:

1. Запустить новый backend-процесс с чистым `Map`.
2. Загрузить типы событий.
3. Получить слот и создать бронь.
4. Убедиться, что бронь отображается в административной части.

Тестовый reset endpoint не добавляется.

## Сборка, CI и Docker

- Backend добавляется как npm workspace.
- Корневые `build`, `typecheck` и `test` проверяют frontend и backend; workspace-команды остаются доступны отдельно.
- Добавляется отдельный CI workflow на Node.js 24. Существующий `.github/workflows/hexlet-check.yml` не изменяется.
- CI проверяет TypeSpec, синхронность всех generated-файлов, typecheck, unit/integration tests, production build и real-backend Playwright smoke после установки Chromium.
- Multi-stage Dockerfile использует конкретный Node.js 24 Alpine tag и непривилегированного пользователя.
- Контейнер использует health check и корректно завершает процесс по `SIGTERM`.

## Этапы реализации

1. Уточнить `main.tsp` по разделу «Контракт».
2. Перегенерировать и проверить OpenAPI и frontend-типы.
3. Добавить `backend` как npm workspace и зафиксировать версии инструментов.
4. Настроить backend codegen из OpenAPI, сгенерировать и закоммитить router, типы и схемы.
5. Реализовать runtime config, clock abstraction, генерацию ID и in-memory store с seed.
6. Реализовать календарную логику чистыми функциями и unit-тестами.
7. Подключить handlers ко всем `operationId` и добавить HTTP integration-тесты.
8. Настроить CORS, JSON/error mapping, health check, логирование запуска и graceful shutdown.
9. Синхронизировать frontend error handling и MSW с контрактом и реальной бизнес-логикой.
10. Добавить real-backend Playwright smoke.
11. Настроить корневые команды и отдельный CI workflow.
12. Добавить и проверить multi-stage Dockerfile.

## Проверка результата

- TypeSpec компилируется без ошибок.
- OpenAPI, frontend-типы и backend generated-код синхронизированы с контрактом.
- Повторная генерация не создаёт diff.
- Backend проходит typecheck, unit-тесты и HTTP integration-тесты.
- Frontend проходит typecheck, unit-тесты, существующие e2e и real-backend smoke.
- Гостевой и административный сценарии работают с реальным backend.
- Backend запускается и корректно завершается локально и в Docker.
- Docker health check проходит.
