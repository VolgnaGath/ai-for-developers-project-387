# Тестирование и пользовательские сценарии

Проверка Call Calendar строится на четырёх уровнях:

| Уровень | Где живёт | Что проверяет |
| --- | --- | --- |
| Unit (Vitest) | `frontend/src/**/*.test.ts`, `backend/test/calendar.test.ts`, `backend/test/normalize.test.ts` | Календарная логика, валидация форм, ошибки API, утилиты |
| HTTP integration (Supertest) | `backend/test/app.test.ts`, `backend/test/server.test.ts` | API-контракт против реального Express-приложения: статусы, коды ошибок, поведение броней |
| UI e2e (Playwright + MSW) | `frontend/e2e/` | Пользовательские сценарии в браузере; stateful и негативные случаи через мок-сервер |
| Real-backend smoke (Playwright) | `frontend/smoke/smoke.spec.ts` | Ключевой путь «гость бронирует → админ видит» против настоящего backend |

## Основные сценарии

| Сценарий | Ожидаемый результат | Где покрыт |
| --- | --- | --- |
| Гость открывает лендинг и выбирает тип события | Лендинг виден, список типов событий публикуется | e2e MSW, smoke, backend HTTP |
| Гость выбирает дату и свободный слот | Календарь в таймзоне конфига, кнопки слотов соответствуют сетке и длительности | backend HTTP, e2e MSW |
| Гость заполняет форму и бронирует | Создаётся бронь, гость видит подтверждение с именем и email | backend HTTP, e2e MSW, smoke |
| Админ видит новую бронь в «Предстоящих встречах» | Бронь появляется в списке с именем гостя и типом события | backend HTTP, e2e MSW, smoke |
| Слот после брони исчезает из свободных | Занятый слот больше не отдаётся сервером и не показывается в UI | backend HTTP, e2e MSW, smoke |
| Гость бронирует уже занятый слот | 409 `slot_unavailable`; UI показывает предупреждение, форму сохраняет, слот сбрасывает и обновляет список | backend HTTP, e2e MSW |
| Гость бронирует несуществующий слот | 422 `invalid_slot`; UI предлагает выбрать другой слот | backend HTTP, e2e MSW |
| Валидация формы брони | Пустое имя и некорректный email не отправляются | backend HTTP, e2e MSW |
| Админ создаёт/редактирует тип события | Изменения сохраняются и появляются на публичной странице брони | backend HTTP, e2e MSW, smoke |
| Админ удаляет тип события без броней | Тип удаляется и пропадает из публичного списка | backend HTTP, e2e MSW |
| Админ меняет длительность или удаляет тип с бронями | 409; операция блокируется | backend HTTP, e2e MSW |
| Слоты за пределами окна бронирования и рабочих часов | Сервер слоты не отдаёт; пустой день показывает «нет свободных слотов» | backend HTTP, e2e MSW |

## Команды

- `npm test` — unit и HTTP integration-тесты фронта и backend.
- `npm run e2e` — Playwright e2e с MSW (поднимает Vite на 5199).
- `npm run e2e:smoke` — Playwright smoke против реального backend (backend на 4020 + Vite на 5199 без MSW).

## Интеграционные проверки

Ключевой путь бронирования против реального backend закрыт `frontend/smoke/smoke.spec.ts`:

1. Гость выбирает тип события и дату, бронирует слот → подтверждение; админ видит бронь; занятый слот исчезает из свободных на ту же дату.
2. Админ создаёт тип события через реальный backend → тип появляется на публичной странице; гость бронирует его слот; админ видит бронь.

В CI эти сценарии запускаются на каждый push и pull request (`.github/workflows/ci.yml`). Smoke не использует retries: реальный backend хранит брони в in-memory-хранилище, и повторный прогон мог бы «загрязнить» данные. Каждый сценарий использует уникальных гостей и разные даты, чтобы не конфликтовать между собой в рамках одного прогона.
